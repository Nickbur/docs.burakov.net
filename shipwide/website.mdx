The marketing site for a single app: a fast, custom-designed site built with **Astro** (static
output), a **hand-written SCSS design system** (no UI framework), **astro-i18next** for
translations, and **Iconify** for icons. No account portal — this is the public marketing site.
Everything ships as placeholder content: drop in your brand, copy and assets and go. See
[Customization](/shipwide/customization) for the design system, [Deployment](/shipwide/deployment)
to ship.

## Quick start

```bash
npm install
npm run switch_to_dev   # env/env.dev → .env
npm run serve           # http://localhost:4334
# production:
npm run switch_to_prod  # env/env.prod → .env (set your domain first)
npm run build           # Prettier check + ESLint + astro-i18next generate + astro check + astro build → static output, then the tests
```

**Tests** (Vitest, run by `build` right after `astro build`): **unit** tests for the TypeScript under
`src/` (coverage gate: 90%), and **smoke** tests in `smoke/` that read the built `dist/` — every page
exists in every language, each has its title, description, canonical and hreflang links, no internal
link or asset points to a missing file, the sitemap and robots.txt match the built pages, and no
`undefined` or raw translation key leaked into the HTML. One file on its own:
`npx vitest run <file> --coverage.enabled=false` (smoke files need a built `dist/`).

## Where things live

| Path | What it is |
|------|------------|
| `src/data/site.ts` | Brand name, email, social links, navigation. **Edit this first.** |
| `src/data/product.ts` | The product: download channels, pricing plans, features, screenshots. |
| `src/screenshots/*.png` | Home hero gallery — name them `01-…`, `02-…` for order. Delete the demo files. |
| `src/data/legal.ts` | Structure of the Privacy / Terms documents. |
| `public/locales/en/*.json` | All human-readable copy, one file per namespace. |
| `src/content/blog/*.md` · `changelog/*.md` | Blog posts / release notes — one Markdown file each. |
| `src/styles/` | The SCSS design system (tokens, base, components, utilities). |
| `src/components/` · `src/layouts/` · `src/pages/` | Astro components, layouts, routes. |

<Note>
    **Rule of thumb:** language-neutral facts (URLs, prices, handles) live in `src/data/`; anything
    a reader sees as words lives in `public/locales/`.
</Note>

## Rebranding (the short path)

<Steps>
    <Step title="Brand & product data">
        Edit `src/data/site.ts` (`name`, emails, socials — the brand name in header/footer/titles is
        driven entirely by `site.name`) and `src/data/product.ts` (download links, prices, features).
    </Step>
    <Step title="Assets">
        Replace the icon set in `public/` (`favicon.ico`, `favicon-16/32/48.png`,
        `apple-touch-icon.png`, `icon-192.png`, `icon-512.png`, `icon-512-maskable.png`) and the
        1200×630 social card `public/og-default.png`, and put your name in `public/site.webmanifest`;
        drop your app screenshots into `src/screenshots/` (`01-…`, `02-…`) and delete the demo images.
    </Step>
    <Step title="Domain & copy">
        Set `PUBLIC_SITE_URL` in `env/env.prod`; swap the copy in `public/locales/en/*.json`.
    </Step>
</Steps>

## Legal documents

The site ships a **Privacy Policy** (`/privacy`) and **Terms** (`/terms`) as a comprehensive
starter template, in English and Russian:

- **Privacy Policy** — GDPR/CCPA-shaped: who is responsible, what's collected and why, legal
    basis, sharing, international transfers, retention, security, data breaches, children, AI &
    machine learning, automated decisions, your rights, plus regional sections for the EEA, UK &
    Switzerland, California (CCPA/CPRA), other US states and Canada (PIPEDA).
- **Terms** — a hardened end-user agreement: license, acceptable use, intellectual property,
    your content, third-party services, purchases & subscriptions, warranty disclaimer,
    limitation of liability, indemnification, termination, governing law & disputes, and the
    Apple & Google store terms the stores require.

**Modular privacy.** List what your app actually does in `privacyModules` in
`src/data/product.ts` — each entry adds one matching section, and anything not listed stays out,
so the policy never over-discloses (a common App Store / Google Play rejection). The modules:
`push`, `payments`, `uploads`, `location`, `contacts`, `camera_media`, `microphone`, `health`,
`financial`, `identity`, `ugc`, `ai`, `ads`. The kit ships with `push`, `payments` and
`uploads`.

**Make them yours:**

<Steps>
    <Step title="Fill in the placeholders">
        Set `legal.company` and `legal.jurisdiction` in `src/data/site.ts` — they replace
        `[Your Company]` and `[your country]` throughout. The contact address is
        `site.supportEmail`.
    </Step>
    <Step title="Match the modules to your app">
        Keep `privacyModules` in step with what the app does; the wording lives in
        `public/locales/<lang>/legal.json`.
    </Step>
    <Step title="Get them reviewed">
        Each document opens with a notice to replace the placeholders and have the text reviewed
        for your jurisdiction. It's a strong starting point, not legal advice.
    </Step>
</Steps>

Point the app at the published pages with `VITE_LEGAL_PRIVACY_URL` / `VITE_LEGAL_TERMS_URL`
(see [App](/shipwide/app)).

## Design tokens & fonts

Colours, fonts, radii, spacing, elevation and motion are CSS custom properties in
`src/styles/_variables.scss`, with light and dark themes:

- **Accent** is a dusty-indigo ramp (`--accent-50…900`) — change `--accent-400` (dark) /
    `--accent-600` (light) and it propagates everywhere.
- **Neutrals** are warm greys, not pure zinc.
- **Fonts are a pairing:** a display face — **Golos Text** — on headings (`--font-display`), and
    the system stack for body/UI (`--font-sans`). The display face is self-hosted: its woff2 files
    sit in `public/fonts/`, declared by the `@font-face` blocks in `src/styles/base/_fonts.scss`, and
    `src/layouts/Base.astro` preloads the weight the page heading uses. To swap it: replace the woff2
    files in `public/fonts/`, update the `@font-face` blocks in `_fonts.scss`, point
    `--font-display` at the new family, and update the preloaded file (`preloadFont`) in
    `Base.astro`. Any OFL font with Cyrillic works; the kit ships one so it's legal to redistribute.

The header theme switcher persists the choice and follows the OS preference until the reader chooses.

## Craft layer

`src/styles/utilities/_effects.scss` holds the depth/motion primitives — all token-driven and
`prefers-reduced-motion`-safe: a designed focus ring, `data-reveal` (fade-up on scroll),
`.spotlight` (cursor-follow on cards), `.ambient-glow` (hero bloom), `.text-gradient`.

Navigation uses Astro **View Transitions** (`<ClientRouter />` in `Base.astro`). The site's scripts
— the reveal/spotlight script in `Base.astro`, the home hero gallery, the header — re-initialise on
every `astro:page-load`.

<Warning>
    Any interactive script you add must bind on `astro:page-load`, not just at module top level: a
    module script runs once, and the elements it bound to are swapped out on the next navigation.
</Warning>

## Languages

Ships **English + Russian**; the switcher is in the header. Adding a third language (e.g. `de`) is
five steps:

<Steps>
    <Step title="Register the code">
        Add it to `locales` in `astro-i18next.config.ts` (`["en", "ru", "de"]`) and to the sitemap
        `i18n` block's `locales` in `astro.config.mjs`.
    </Step>
    <Step title="Wire the components">
        Add it to `locales` in `src/components/Header.astro` and a label under `langs` in every
        `public/locales/*/nav.json`; to `LOCALES` in `src/layouts/Base.astro` and
        `src/components/Breadcrumbs.astro`; and to `inLanguage` in
        `src/components/StructuredData.astro`. `Base.astro` also maps each language to its Open
        Graph locale (`ogLocale`) and preloaded font subset (`preloadFont`) — extend both.
    </Step>
    <Step title="Allow it in the content schema">
        Add it to both `lang: z.enum([...])` lists (blog, changelog) in `src/content.config.ts`.
    </Step>
    <Step title="Translate">
        Copy `public/locales/en/` → `public/locales/<code>/` and translate. For blog/changelog, add
        `<slug>-<code>.md` with `lang: "<code>"`; a blog translation carries the same
        `translationKey` as the other language versions of that post — that's what links them for
        hreflang.
    </Step>
    <Step title="Build">
        `npm run build` runs `astro-i18next generate`, producing the localized page tree under
        `src/pages/<code>/` — rebuilt each build, never edited. Add `src/pages/<code>/` next to
        `src/pages/ru/` in `.gitignore` and in the ESLint ignores in `eslint.config.mjs`.
    </Step>
</Steps>

English-only: drop `"ru"` from those lists and delete `public/locales/ru/` + the `*-ru.md` files.

<Warning>
    `src/pages/ru/` is **generated** by `astro-i18next generate` at build and git-ignored — edit the
    English source; the Russian tree regenerates.
</Warning>

**Generator gotchas:**

- **No `---` after a page's closing frontmatter fence** (e.g. a `// --- section` comment in a
    `<script>`): `astro-i18next generate` matches the frontmatter greedily and rewrites the
    **English source** into unparseable output. Inside the frontmatter it's fine.
- The localized copy sits one folder deeper, and only the frontmatter's relative `import` paths
    are rewritten — write path strings such as `import.meta.glob` root-relative (`/src/…`), and
    import `src/data/` into a page `<script>` through the `@data/*` alias.
- Locale JSON is read once at dev-server start — restart `npm run serve` after editing
    `public/locales/*`.

## Content, support form, monitoring

- **Blog & changelog** are Astro content collections — add a Markdown file, it appears. Schemas in
    `src/content.config.ts`. Pages read from `src/data/` + locale JSON, so nothing is hardcoded.
- **Support form:** set `PUBLIC_SUPPORT_ENDPOINT` to the full URL of your API's
    **`POST /v1/support`** (e.g. `https://api.example.com/v1/support`) and add the site's origin to
    the API's `CORS_ORIGINS`. It posts without an account; the API emails each message to its
    `MAIL_REPLY_TO` (Reply-To = the sender, so you answer from your mail client), allows 5 messages
    per IP per 10 minutes, and silently drops bots (a hidden honeypot field + a minimum fill time).
    Empty (default) = **demo mode**: it validates but shows an "email us" notice instead of
    posting. No code change on launch day — set the variable and rebuild.
- **Sentry** loads only when `PUBLIC_SENTRY_DSN` is set, cookies are accepted, and it's not
    `localhost`. Empty DSN = off.
