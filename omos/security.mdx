OMOS is designed around **capabilities**: a program can act on a kernel object only through a **handle** to it,
and each handle carries a set of **rights**. This page describes what's enforced today and, just as importantly,
what isn't yet.

## Handles and rights

Each process has its own handle table. A handle names one kernel object and the rights the process holds on it.

| Right | Allows |
| --- | --- |
| Read, Write | Reading from and writing to the object |
| Execute | Executing it (code) |
| Map | Mapping it into memory |
| Transfer | Sending the handle to another process in a message |
| Duplicate | Making a copy of the handle |
| Signal, Wait | Signalling the object and waiting on it |
| Enumerate | Listing its contents |
| Destroy | Destroying it |

**Rights can only shrink.** Duplicating a handle needs the Duplicate right and can drop rights, never add them;
sending a handle needs the Transfer right and moves it out of the sender's table.

## Object types

Twelve kinds of kernel object are reached through handles: process, channel, notification, timer, memory region,
shared memory object, device I/O region, interrupt, job, file, wait set and PCI device.

## What's isolated today

- Every service and driver runs in **user mode** in its **own address space**, with page permissions set per program
    segment.
- The kernel and programs are loaded at **randomized addresses**, and stacks have guard pages.
- System calls that take a handle check that the handle exists and carries the needed right.
- The service manager starts each built-in service with only the handles it needs: the serial log, its IPC
    channels, and the PCI devices that match its driver.

## Current limitations

The model isn't complete yet. Today:

- **Hardware access isn't gated by capabilities.** The system calls drivers use to reach device memory, I/O ports,
    interrupts, DMA memory and PCI devices don't require a handle — any user-space program could use them.
- **File access is ambient.** Files are opened by absolute path in one shared namespace; there are no per-directory
    capabilities yet.
- **A fault anywhere stops the system.** A crash in a user-space driver or service halts the whole machine — there's
    no fault isolation or restart yet.
- **No IOMMU protection.** Drivers that use DMA aren't restricted to their own memory.
- **Resource quotas aren't enforced** for jobs.
- **Randomness is weak.** The entropy source isn't cryptographic, and the randomization range for program code is
    limited (around 18 bits).

These are expected for a developer preview, and they're why OMOS shouldn't run anything you need to protect. Closing
them is part of the [roadmap](/omos/roadmap).
