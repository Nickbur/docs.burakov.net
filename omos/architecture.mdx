OMOS uses a **hybrid kernel**: core hardware support lives in the kernel, while storage and input drivers and the
filesystem service run as separate programs in user space, each in its own address space, talking to each other
through [IPC channels](/omos/ipc).

## What runs where

| In the kernel | In user space |
| --- | --- |
| Memory management, scheduler, multicore, power | **`svc:vfs`** — the filesystem service |
| IPC, capability handles, system calls | **`drv:virtio-blk`** — virtio block devices |
| Interrupt controllers and timers | **`drv:nvme`** — NVMe drives |
| ACPI and device-tree discovery, PCI configuration | **`drv:ahci`** — SATA drives |
| Serial output, the text display, the PS/2 keyboard (x86) | **`drv:fat32`** — the FAT32 filesystem |
| The read-only boot archive, file-path routing, the program loader | **`drv:virtio-input`** — virtio keyboards and other input |

See [Kernel](/omos/kernel) and [Drivers & storage](/omos/drivers-and-storage) for each side.

## Boot flow

<Steps>
    <Step title="UEFI firmware">
        Starts the Limine bootloader from the ISO. OMOS requires UEFI.
    </Step>
    <Step title="Limine">
        Loads the kernel at a randomized address (KASLR) together with the boot archive, and hands over the memory
        map, firmware tables and display.
    </Step>
    <Step title="Kernel start-up">
        Sets up the CPU, interrupts, memory, the boot archive, device discovery, timers, the display and the other
        cores.
    </Step>
    <Step title="Service manager">
        Loads the six built-in services from the boot archive in a **suspended** state, creates the IPC channels
        between them, gives each one the handles it needs, then resumes them all.
    </Step>
</Steps>

## How the parts are connected

- The **filesystem service** receives file requests from the kernel and passes them to the **FAT32** driver.
- **FAT32** reads and writes blocks through the **virtio block** driver.
- The **NVMe** and **AHCI** drivers detect their disks, but no filesystem is connected to them yet.
- The **virtio input** driver reports key events to the serial log.
- Drivers reach their PCI devices through handles the service manager grants, matched by vendor and device ID or by
    device class.

## The boot archive

The ISO contains the kernel and a read-only archive (initrd) mounted at `/`:

```text
/etc/version           OMOS v1.0.0 (Sirius)
/etc/system.conf       Placeholder, not read yet
/system/services/vfs   The filesystem service
/system/drivers/…      virtio_blk, nvme, ahci, fat32, virtio_input
```

Paths that aren't in the archive are forwarded to the filesystem service, and from there to the FAT32 disk.

## Written in Rust

The kernel, drivers and services are written in Rust without the standard library (`no_std`), built with the
nightly toolchain for three targets: x86_64, AArch64 and RISC-V 64.
