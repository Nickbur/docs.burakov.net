## The judge witnesses, it doesn't opine

Most AI coding tools ask a second model whether the first one did a good job. Their mistakes tend to be
the same mistakes. Remigent doesn't do that.

Its judge **binds every verdict to executed reality**: the code compiles, the tests pass, the scanners
are clean, the API answers, the app actually renders the screen. Nobody can talk their way past a
compiler, a test run or a real browser. A model's opinion is used only as a soft signal on the rare parts
that can't be executed — never as the verdict.

## Separation of powers

- **The judge brings its own checks**, written from the agreed plan — the way an independent QA team writes
  tests from requirements.
- **The code's author never sees them.** It writes the code and its own development tests, but can't read,
  influence or game the checks that judge it.
- **The judge works on a fresh copy of the exact commit** being proposed — never on the author's working copy.

After you merge, what the judge learned stays behind as **permanent checks** that protect every later change.

## "Green" isn't enough

A passing test suite can still be wrong. Remigent closes the gap from several sides:

- **It proves the checks actually catch bugs**, instead of trusting that a passing suite means correct code.
- **It tests beyond hand-picked examples.**
- **Every escaped defect becomes a permanent check**, so the same class of bug is caught across your
  whole fleet from then on.
- **What can only be judged in use** — is the new flow better? — is made reversible (feature flags,
  safe migrations) and checked against real signals after you ship.

## What gets checked

| Area | What is verified | Applies to |
|---|---|---|
| **Every change** | your build, tests and linters from the recipe; the judge's own checks; security and dependency scans; the change staying within its scope | every stack |
| **Tests and tidiness** | tests come with the code they cover (expected, or required — your choice); the tests are never weakened — no skipped or focused tests, no lowered coverage thresholds, no new exclusions; no debug output, temporary or stray files left in the change | every stack |
| **Living docs** | the documentation you declared living — and the interface copy — matches what is actually built | every stack |
| **Web UI** | the running app on its key routes — rendering, errors, screen sizes and themes, accessibility and visual changes | any web front end — including Capacitor/Ionic apps through their web build, and Astro sites |
| **HTTP API** | the running service, tested from the outside, including against your latency budget | any backend |
| **Test strength** | that the tests catch real mistakes and hold beyond hand-picked examples | by ecosystem |

**Full coverage** (every area): JavaScript/TypeScript (Node, Vue, React, Ionic web, Astro), Python, Rust
and Go. **Other stacks** (PHP, Java, …) get the recipe, the checks every change gets, and the web and API checks
where they apply. **Native apps** get their build and unit tests, plus the web layer when there is one.
iOS builds need a [self-hosted runner](/remigent/self-hosted-runner) on a Mac.

<Note>
    Verification is never skipped or weakened to save money. If the checks an item needs don't fit the
    budget, the item doesn't start.
</Note>

## What's on every pull request

Each pull request follows the same template, with the details folded away until you need them:

- what was built and why;
- the judge's **evidence** and a **coverage map** — what was verified and how, and **what wasn't and
  why**;
- the decisions made along the way;
- the blast radius — what the change can affect;
- the expected cost and impact;
- for work across several repositories, the linked pull requests and their merge order.

The goal is to make merging a quick, confident decision.

## After you merge

Remigent never deploys and never touches production — your CI/CD does. What it can do is watch the
signals you've connected (errors, store reviews, support, analytics, uptime) for a window after the
merge, 72 hours by default:

- **If things got worse**, it opens an urgent revert or flag-off pull request and notifies you. You merge
  it and your pipeline rolls back.
- **If nothing is connected**, it says so on the pull request instead of pretending the result was
  observed.
