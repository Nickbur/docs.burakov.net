## The judge witnesses, it doesn't opine

Most AI coding tools ask a second model whether the first one did a good job. Their mistakes tend to be
the same mistakes. Remigent doesn't do that.

Its judge **binds every verdict to executed reality**: the code compiles, the tests pass, the scanners
are clean, the API answers, the app actually renders the screen. An executor can't talk its way past a
compiler, a fuzzer or a real browser. A model's opinion is used only as a soft signal on the rare parts
that can't be executed — never as the verdict.

## Separation of powers

- **The judge writes its own exam** from the plan — black-box acceptance tests, the way an independent QA
  team writes tests from requirements.
- **The executor never sees the exam.** It writes the code and its own development tests, but can't
  read, influence or game the acceptance tests.
- **The judge runs on a fresh sandbox at the exact commit** being proposed — never on the executor's
  working copy.
- **The model that writes the exam comes from a different model family** than the one that wrote the
  code, so their blind spots don't line up.

After you merge, the exam **graduates**: its tests become permanent regression checks in
`.remigent/checks/`, and the next change gets a new hidden exam.

## "Green" isn't enough

A passing test suite can still be wrong. Remigent closes the gap from several sides:

- **Mutation testing** on the changed lines proves the checks actually catch bugs.
- **Property and fuzz tests** go beyond hand-picked examples.
- **Every escaped defect becomes a permanent check**, so the same class of bug is caught across your
  whole fleet from then on.
- **What can only be judged in use** — is the new flow better? — is made reversible (feature flags,
  safe migrations) and checked against real signals after you ship.

## The check layers

| Layer | What runs | Applies to |
|---|---|---|
| **Universal** | your build and tests from the recipe; the judge's acceptance tests; secret scanning (gitleaks); vulnerable dependencies (osv-scanner); static analysis (Semgrep); the change staying within its scope; your linters | every stack |
| **Web UI** | Playwright in Chromium: every key route renders, no new console errors, two viewports, light and dark, accessibility (axe), screenshot comparison against the base | any web front end — including Capacitor/Ionic apps through their web build, and Astro sites |
| **HTTP API** | the service is started with its dependencies and tested black-box; a load test against your latency budget | any backend |
| **Properties & fuzzing** | fast-check, Hypothesis, proptest | by ecosystem |
| **Mutation** | Stryker, mutmut, cargo-mutants — changed lines only | by ecosystem |

**Full coverage** (every layer): JavaScript/TypeScript (Node, Vue, React, Ionic web, Astro), Python, Rust
and Go. **Other stacks** (PHP, Java, …) get the recipe, the universal layer, and the web and API layers
where they apply. **Native apps** get their build and unit tests, plus the web layer when there is one.
iOS builds need a [self-hosted runner](/remigent/self-hosted-runner) on a Mac.

<Note>
    Verification is never skipped or weakened to save money. If the checks an item needs don't fit the
    budget, the item doesn't start.
</Note>

## What's on every pull request

Each pull request follows the same template, with the details folded away until you need them:

- what was built and why;
- the judge's **evidence** and a **coverage map** — what was verified and how, and **what wasn't and
  why**;
- the decisions made along the way;
- the blast radius — what the change can affect;
- the expected cost and impact;
- for work across several repositories, the linked pull requests and their merge order.

The goal is to make merging a quick, confident decision.

## After you merge

Remigent never deploys and never touches production — your CI/CD does. What it can do is watch the
signals you've connected (errors, store reviews, support, analytics, uptime) for a window after the
merge, 72 hours by default:

- **If things got worse**, it opens an urgent revert or flag-off pull request and notifies you. You merge
  it and your pipeline rolls back.
- **If nothing is connected**, it says so on the pull request instead of pretending the result was
  observed.
