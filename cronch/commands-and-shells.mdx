A rule runs one command. Cronch's job is to run it the way you'd run it yourself, and to record what happened.

## The command

Type the command, or the path to a script, exactly as you would in a terminal. Cronch hands it to the shell you choose to interpret — so pipes, redirects and arguments work as usual.

Two things are different from a terminal:

- **There's no keyboard.** Jobs get no input, so anything that waits for an answer — a confirmation prompt, a password prompt, `sudo` — can't complete. Use flags like `--yes`, or set up the tool so it doesn't ask.
- **There's no interactive shell.** Your aliases and shell functions aren't available, and PowerShell runs without your profile. See [Environment & working directory](/cronch/environment).

## The shell

When Cronch starts, it looks for the shells installed on your computer — using your login `PATH`, so a shell installed with Homebrew is found even when Cronch was started at login. The editor's **Shell** list offers what it found:

| System | Shells (as named in the list) | How the command is passed |
| --- | --- | --- |
| **Windows** | Command Prompt (cmd) | `cmd /S /C <command>` — your command exactly as typed, quotes included |
| | Windows PowerShell | `powershell -NoProfile -Command <command>` |
| | PowerShell 7+ | `pwsh -NoProfile -Command <command>` |
| | Git Bash | `bash -c <command>` |
| | WSL (bash) | `wsl -e bash -c <command>` |
| **macOS** | Zsh, Bash, sh | `<shell> -c <command>` |
| | fish | `fish -c <command>` |

So `"C:\Program Files\App\app.exe" --flag` works in Command Prompt just as it does in a terminal window. A shell you install while Cronch is running shows up after you restart Cronch.

**Git Bash** is the `bash.exe` of your Git for Windows install, wherever Git is installed. Windows' own `bash.exe` is the WSL launcher, so it is never offered as Git Bash — pick **WSL (bash)** for that.

You also get two special choices:

- **Custom…** — point at any shell binary (**Shell binary path**) and give the **Argument template** to use. The template must contain `{cmd}`, which Cronch replaces with your command; the default is `-c {cmd}`. The template is split into arguments using your system's quoting rules.
- **Direct (no shell)** — run an executable straight, with no shell involved. The command line is only split into program and arguments: shell-style quoting on macOS, and Windows command-line rules on Windows (backslashes in paths are kept; put a path that contains spaces in double quotes). Pipes, redirects and variables don't work here, because nothing interprets them.

<Note>
    If a rule names a shell that isn't installed on the current computer, the rule list shows **⚠ shell missing**, and the editor shows it as *(not found on this machine)* until you pick another. If such a rule comes due, the run fails with *shell '…' not found on this machine* instead of running something else. This keeps imported rules honest: on a new computer you see at a glance what it can and can't run.
</Note>

## What counts as success

A run is **Success** when the command exits with code **0**, and **Failed** for any other exit code. Cronch records the exit code, everything the command printed to stdout and stderr (up to 256 KB of each), and what triggered the run — see [History & logs](/cronch/history).

## Timeout

Each rule has a **Timeout**: *Kill after N seconds*. New rules get **300 seconds (5 minutes)**; you can set up to **604,800 seconds (7 days)**, or **0** for no limit.

When the timeout runs out, Cronch **force-stops the command together with everything it started** — there's no graceful shutdown signal — and records the run as **TimedOut**. Give long jobs such as backups a generous timeout, and make sure they can survive being interrupted.

## Programs left running in the background

If your command starts a program in the background and exits (a server started with `&`, or `start` on Windows), the run is finished as soon as the command itself exits; the background program keeps running. Cronch waits two more seconds for output, then notes in the run's stderr that a background process still holds its output — anything it prints after that isn't recorded.

## Overlap: when a run isn't finished yet

If a rule comes due while its previous run is still going, its **If already running** policy decides what happens:

| Policy | What it does | Good for |
| --- | --- | --- |
| **Skip** *(default)* | Doesn't start a second run. The history gets a **Skipped** row instead, and the rule keeps showing **Running**. | Backups, anything that must never run twice at once. |
| **Queue** | Waits for the current run to finish, then runs once more. At most **one** run waits per rule — if it comes due again while one is already waiting, that run is skipped. The waiting run is dropped if you switch the rule off, pause everything or quit Cronch. Each run that doesn't happen shows in the history as **Skipped**. | Jobs where the next occurrence should still happen, in order. |
| **Parallel** | Starts the new run immediately, alongside the current one. The rule's status updates when the last of them finishes. | Short, independent tasks that are safe to overlap. |

**Run now** follows the same policy — with **Skip**, Cronch tells you *Already running — this run was skipped*.

Deleting a rule stops any run of it that is still going.
