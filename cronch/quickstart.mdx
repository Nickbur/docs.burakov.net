There are two ways to get Cronch. Download a ready-made build, or build it from source.

## Option A — Download

<Steps>
    <Step title="Get the app">
        Download the build for your system from the [Cronch project page](https://burakov.net/projects/cronch) — a `.exe` for Windows (x64 or ARM64), or a `.dmg` for macOS (Apple Silicon or Intel). The same files are on the [Releases page](https://github.com/Nickbur/cronch/releases) on GitHub.
    </Step>
    <Step title="Put it where it will stay">
        On macOS, drag Cronch into **Applications** before you open it for the first time. On Windows, put the `.exe` in a folder you won't clean up. Cronch registers itself to launch at login from wherever it's running on first start, so starting it from your Downloads folder and moving it later breaks that link (see [Troubleshooting](/cronch/troubleshooting#cronch-does-not-start-at-login-after-moving-the-app) if it already happened).
    </Step>
    <Step title="Open it">
        Run the app. A window opens and the Cronch icon — a green loop arrow — appears in your system tray (Windows) or menu bar (macOS). A one-time banner tells you that Cronch now launches at login; click **Got it**.
        <Note>
            The downloads are code-signed for Windows and signed and notarized by Apple for macOS, so they open like any other app. A copy you build yourself or get from somewhere else is unsigned and can trip Windows SmartScreen or macOS Gatekeeper — see [Troubleshooting](/cronch/troubleshooting).
        </Note>
    </Step>
</Steps>

## Option B — Build from source

Cronch is open source. If you'd rather build it yourself, you need a recent stable Rust toolchain (1.85 or newer) and a system linker: the MSVC toolchain on Windows (Visual Studio Build Tools with the **Desktop development with C++** workload), or Apple's Xcode Command Line Tools on macOS.

<Steps>
    <Step title="Clone the repository">
        ```bash
        git clone https://github.com/Nickbur/cronch.git
        cd cronch
        ```
    </Step>
    <Step title="Build the release binary">
        ```bash
        cargo build --release
        ```
        The binary lands at `target/release/cronch` (or `cronch.exe` on Windows). For a quick try-out, `cargo run` builds a debug copy and starts it straight away, with logs printed to the terminal; it runs as a separate *Cronch-Dev* app with its own rules and data, and never turns on launch at login by itself. The full step-by-step, including how to install the toolchain, is in `BUILD.md` in the repository.
    </Step>
</Steps>

## Create your first rule

<Steps>
    <Step title="Add a rule">
        Click **+ Add rule** in the header (or **Add rule…** in the tray menu). Give it a name you'll recognise later, like "Nightly backup".
    </Step>
    <Step title="Enter the command">
        Type the command or the path to a script — exactly as you'd type it in a terminal.
    </Step>
    <Step title="Pick a shell">
        Choose one of the shells Cronch detected on your machine, a custom shell binary, or **Direct (no shell)** to run an executable without a shell. See [Commands & shells](/cronch/commands-and-shells).
    </Step>
    <Step title="Choose a schedule">
        Pick **Interval**, **Cron**, or **Once**, and fill in the timing. New rules start as **Interval, every 5 minutes**. See [Choosing a schedule](/cronch/schedules).
    </Step>
    <Step title="Save">
        Click **Save**. The rule appears in the list, switched **on**, with its **next** run time. Cronch takes it from there.
    </Step>
</Steps>

<Tip>
    Want to check it works right away? Click **Run now** on the rule, then open its **Logs** to see the captured output. A manual run doesn't move the schedule. It only works while the rule is switched on, and it follows the rule's overlap policy — if the previous run is still going and the policy is **Skip**, Cronch tells you the run was skipped.
</Tip>
